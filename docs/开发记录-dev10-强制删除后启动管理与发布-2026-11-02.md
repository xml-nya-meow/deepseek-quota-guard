# dev10：强制删除后启动管理与发布（2026-11-02）

版本：`0.1.0rc6.dev10`，候选预发布。用户授权修复后更新 GitHub；本轮不访问真实平台账户、不调用付费 API、不撤销真实 Key。已有 dev6～dev9 改动继续保留并纳入本版，旧包和真实账本不覆盖。

## 一、实际改动

- 强制删除所用的身份读取会清除旧费用核验。现在用户明确点击“启动全自动管理”时，程序在现有浏览器会话重新读取完整 Key 列表和费用，核验成功后进入原有启动确认，无需先中断或重登录。
- 这次启动前读取本身不启动管理；未点击启动时，强制删除仍只处理选中目标。启动前读取期间显示明确状态，“停止管理”可取消后续启动；重复点击不会重复读取。
- 本地读取同步报错或无费用结果在续接启动前过期时，也清理待启动标记并保留未开启状态，避免控件持续被占用。读取异常可修复后重试，过期证据仍须重新核验。
- 后续启动绑定本次账本、会话、人员表哈希、管理代次及新核验结果。停止、登录、中断、关闭、切换账本、人员表变化、读取失败、认证失效或旧删除结果未知，均不会继续开启管理或自动重试删除。新的启动仍需原有一次整体确认，不新增逐枚审批。
- 手动重新读取已经完成时，启动不重复读取。正额度费用有效期、未知费用不按零计算、空名行不参与管理、`-1` 跳过及 `0` 零额度规则不变；本次没有通过延长或复用旧核验来绕过检查。
- README、使用说明、验证计划和测试历程明确写出：大于 0 的斩杀线／个人额度下，真实消费跨线、周期读取及自动撤销的完整流程尚未验证；Excel 模板导入后转为内置两列表的真实操作验收仍暂缓。
- 建议使用可正常运行的闲置专用电脑持续运行。其他同机操作可能干扰；并行使用、长期无人值守等场景未完成专项测试，不能保证没有问题。问题反馈应附版本、情况说明、复现步骤和检查脱敏后的诊断日志，不提交完整 Key、凭据或原始账本。
- GitHub 交付范围限定为源码、测试、空白模板及文档；干净 Windows 便携候选包单独本地交付。已用于真实测试的 dev9 目录不用于打包，GitHub 仓库不含真实账本、浏览器会话或诊断日志；本轮沿用普通源码推送流程，不创建二进制 Release。

## 二、改动理由

用户反馈强制删除成功后，启动全自动管理像失效，必须中断后重新登录才能成功。对本地 dev9 日志的只读核对显示：2026-11-02 15:37:57（UTC+8）强制删除已确认目标不存在；随后多次点击启动均立即返回，程序并不忙，也没有派发新的费用读取。中断重登录后，15:38:45 读取完成、15:38:48 启动成功。

源码对应断点是强制删除身份核验主动清除 `collection_context`，而启动入口只提示重新读取，没有继续衔接。浏览器工作进程已更新删除后的 Key 集合，UI 的单次操作状态也已清理；没有证据表明这次必须重建浏览器。修复是在显式启动时补齐新的只读核验，并保留取消与确认边界。

同一份日志还记录到 15:38:53、15:38:59、15:39:05 三次自动撤销确认目标不存在，随后用户停止管理。这证明本次零额度首轮连续处理已成功；读取结果为 `NO_USAGE_DATA`，且没有据此证明后续周期读取，所以不能宣称正额度真实跨线或完整周期调度已验收。本文仅总结结果，不公开原日志、目标标识或凭据。
