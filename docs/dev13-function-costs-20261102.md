# dev13：函数费用正式解析与自动管理回归

日期：2026-11-02；本地候选。此轮包含 dev12 日期诊断及上下文保护，并处理用户随后补充的函数费用问题。

## 实际改动

- 正式费用解析共同汇总 `series` 与 `function_series` 的 `buckets[].cost`，按 Tracking ID 得出周期累计。纯函数消费也能形成有效金额，不再仅因函数系列非空就拒绝。
- 两类费用使用相同的币种、完整期间、UTC+8 分桶、金额精度、Key 标识与重复桶检查。每类内部出现重复桶时拒绝；模型桶和函数桶属于不同类别，不能跨类别错误去重而漏费。
- 已明确存在函数类别元数据却缺少函数系列时拒绝；函数元数据或费用结构异常时拒绝整份结果，不只采用模型小计。没有函数计费提示的旧格式仍保留兼容。
- 直接使用平台返回的金额，不以 Search/Fetch 次数、token 数或价目表估算，不重复加入顶层合计，不猜测函数标签名称。
- 函数桶数量及最早/最晚时间使用独立诊断字段；旧 `bucket_count` 继续只表示模型桶，避免前后日志语义改变。
- 自动管理因费用不可用、不可重试且没有合格目标而停止时，记录明确原因码；提示不再让人误以为按钮从未启动。没有修改零额度、正额度、`-1` 跳过或强制删除规则。
- 继承 dev12 的结果摘要、匿名平台/账本覆盖计数、日期不变量验证和采集上下文保护。完整 UUID 大小写等价计数仅用于诊断，不迁移绑定或放宽身份检查。

## 改动理由

用户新提供的 12 份日志共 45,836 条记录，读取前后摘要一致。其中六次独立查询均为 2026-11-02 当日，HTTP 与业务成功，响应有一个模型系列和一个函数系列；正式解析器随后返回 `CHARGE_TYPE_UNSUPPORTED`。中断重登录后仍重复出现，因此这六次的直接原因是现有代码主动拒绝函数费用，不是只有历史日期不能读。

旧日志的 24 个费用桶仅是模型桶计数，函数桶结构、函数名称和真实金额没有保存；不能从日志数量声称已完成实际金额对账。

[官方价目表](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/) 与 [Search/Fetch 指南](https://api-docs.deepseek.com/zh-cn/guides/search/) 明确存在独立工具费用。此前保存的[官方前端静态文件](https://fe-static.deepseek.com/platform/static/4179.a95866c86d.js) 将同一费用接口的模型系列和函数系列映射为相同的 Key、分类、时间桶、金额结构，再连接两类系列，以 Decimal 累加每个桶的实际金额。这为正式适配提供了具体实现依据；控制台内部接口仍不等于官方承诺稳定的公开账单 API。

该前端样本 SHA-256 为 `7c92bdb484b6bfc54aee93723f1b35915447434d0628fafb064fc4a1706d5bc1`；采集时保留的摘要与本轮重算一致。映射与合计逻辑位于约 521149、566854、570517 字符附近。这些位置对应已保存的样本，不保证未来在线文件不变化。

强制删除与费用核算仍独立：新日志中三次真正提交的撤销最终均记录目标缺席核验；另一次失败在 `read_keys` 返回后的本地处理，未进入删除提交，旧日志不足以确诊该次 GuardError。强制删除能用不代表费用已完整，函数费用缺失也不应阻止用户明确授权的独立强制入口。

1. **函数费用真实对账尚未完成。** 新包按已观察的官方前端结构严格解析，需要用户先保持全自动管理停止，在相同期间读取并核对官方金额。异常结构仍应拒绝，不绕过校验。
2. **历史费用零匹配的归属原因仍未确认。** 不同日期账本账户和绑定相同，已排除本次日期改身份的猜测；但现有日志不足以确认未匹配费用属于哪些 Key。需要新匿名覆盖诊断，不按姓名合并。
3. **09-29 起点业务拒绝的具体原因仍未知。** 不硬编码猜测的 30 天上限，不自动缩为当天，不实施未经验证的分块合并。
4. 真实正额度消费跨线后周期读取并自动撤销的完整闭环、Excel/WPS 实际导入、长期运行与同机干扰仍未验收。离线假撤销不能代替真实闭环。
5. 旧日志中一次强制删除前本地 GuardError 的具体分支待确认；不把当时尚未提交误标为平台删除失败。删除后旧 Key 调用端拒绝也未额外实测。
6. dev10 托管 CI 的布局问题仍独立保留。本轮没有操控 Harness、消耗 DeepSeek 模型或搜索额度、修改真实账本、覆盖旧包或改动私库固定归档。
