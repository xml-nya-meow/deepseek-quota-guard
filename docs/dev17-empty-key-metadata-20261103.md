# dev17：达额后删除准备失败的调查与修复（2026-11-03）

版本：`0.1.0rc6.dev17`，本地候选。基于 dev16 提交 `6a4de98` 建立独立工作目录，保留旧源码、旧包、日志和真实账本。本轮不访问真实账户、不调用付费 API、不提交真实删除，也没有提交或推送 GitHub。

## 一、实际改动

1. **区分普通 Key 与 Harness 管理的 Key。** HTTP 列表中明确标为 `DSH` 的条目只提供完整 Tracking ID 身份锚，不生成普通 Key 的删除参数；普通 `USER` 仍完整校验名称、UUID、脱敏标识和创建时间。未知或缺失的 `key_type` 返回 `KEY_KIND_INVALID`，不猜测类型。
2. **保留完整身份核验。** DSH 按已观察的官方显示规则匹配 `DeepSeek Harness` 和可选 `App-managed` 标记，名称只能完整匹配；不采用包含匹配，不根据名字推断类型，不删除普通 Key 名称中的任意后缀。完整 UUID 集合、数量、唯一性与普通名称仍必须一致。
3. **禁止把 DSH 当普通 Key 删除。** 选中 DSH 时明确返回 `KEY_TARGET_NOT_DELETABLE`。只有当次核验签发的普通 `DeleteTarget` 才能提交一次；没有给空 `sensitive_id` 补值，也没有改成仅凭姓名或 UUID 删除。
4. **保持删除后双重核实。** 当前准备通过的 DSH 显示名只在本次管理器会话中按 UUID 保存；后续 HTTP 列表保留该名称，再与独立刷新后的网页列表比对。新准备、失败、清理或重新捕获授权时失效。提交后出现新的 DSH 或已知条目类型变化时拒绝核实，不自动重发。
5. **补充有限诊断。** 字段错误新增 `key_kind=USER/DSH/unknown`，只允许这三个固定值；任意返回内容不原样进入日志。保留字段存在性、类型、封顶长度和行序号，帮助下一次只读检查区分实际是哪类条目。
6. **补充不连续填写回归。** 用户随后澄清，三条实际 Key 记录中的第三条之前夹有十多行未填写标识、个人额度为 `-1` 的空行，空行只显示默认公共平均额度。新增精确布局和 HTTP 列表排列的合成测试；这一补充没有改动运行代码或重新构建 EXE。

原额度规则、费用查询范围、完整身份保护、未决操作责任及最后一枚 Key 限制不变。此处处理的是删除准备的列表契约，不修改费用请求或日期基线。

### 已确认事实与待确认解释

- **已确认：** 首行 `sensitive_id` 为空使完整列表校验失败；此前网页身份列表和管理授权已经通过。不是这次授权头缺失，也没有证据说明日期基线导致本次失败。
- **已确认的实现缺口：** 原适配器把所有列表条目都当成普通可删除 Key，没有识别平台前端已有的 Harness 管理类型。合成混合列表可复现相同错误。
- **尚不能确认：** 旧日志没有 `key_type`，不能仅据此认定现场首行一定是 DSH，也不能判断它是被选目标还是另一个条目。若现场其实是普通 USER 的字段为空，dev17 仍会拒绝，并提供明确类型诊断；不会为求通过而放宽真实删除条件。
- **金额边界：** 日志记录了费用应用状态、覆盖条数和自动管理动作，但没有精确费用/额度值。不能由这批日志重建具体金额，或宣称正额度真实跨线到成功删除的闭环已验收。

### 适配依据

依据是此前从官方开放平台取得并保留的公开前端静态文件 `4179.a95866c86d.js`（2026-10-31），SHA-256：`7c92bdb484b6bfc54aee93723f1b35915447434d0628fafb064fc4a1706d5bc1`。其中 `key_type === "DSH"` 映射到 Harness 管理项，显示固定本地化名称和 `App-managed` 标记，Key 列显示“由 Harness 管理”，普通编辑/删除按钮禁用。其普通删除请求仍携带 `redacted_key`、`created_at` 和 `tracking_id`。

这支持“DSH 只作身份锚、不能走普通删除”这一有限修正，**不支持接受任意空普通 Key 字段，也不是官方公开管理 API 的稳定承诺**。本轮没有登录当前平台重取契约；未登录公开访问返回 403，因此没有把缓存资料说成实时服务端验证。`USER` 分支沿用现有普通 Key 契约夹具，不声称缓存 JS 直接证明所有普通枚举值。

### 用户补充：第三条记录前有十多行空白

用户描述中的 a/b/c 是实际 Key 记录的代称，并非填写了这三个字母。中间行未填写标识，个人额度为 `-1`，仍显示公共人均额度。代码沿途通过名称建立唯一 Tracking ID 绑定，再按该 ID 查费用、评估和提交目标；没有把人员表第 N 行当成平台列表第 N 行，也没有在首个空行停止遍历。空名优先判为未分配，默认公共额度不会让空行参与管理。相关 core/UI/浏览器流程与 dev16 的文件哈希一致。

日志中 `count=1` 是 **HTTP 响应列表第一行**，不是表格第一行，也不证明是 c 的字段为空。离线反例证实：选中 c，另一个普通 Key 的 `sensitive_id` 为空，也会报该原因码。此补充未复现行号错位，不能据此要求用户把名单压紧或移走空行；现场空字段的类型仍需 dev17 只读诊断。
