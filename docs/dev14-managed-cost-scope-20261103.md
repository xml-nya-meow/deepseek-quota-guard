# dev14：只查询受管 Key 的费用

日期：2026-11-03；本地候选，未发布运行代码。

## 实际改动

- GUI 只把已填写名称且个人额度不为 `-1` 的人员交给费用采集。没有受管人员时不启动浏览器费用任务；空姓名即使填了零或正数也不进入查询。
- 在当前平台列表中解析明确 Tracking ID，费用 GET 传入重复的 `api_key_tracking_id` 参数。多枚受管 Key 合并为一次带筛选的请求；空范围拒绝，不能变成全账户查询。
- 费用授权通过独立浏览器的确切 Key 列表 GET 建立，不打开用量页以免触发默认全账户费用请求。沿用会话内存授权，不读日常浏览器资料或模型密钥。
- 请求参数、响应里的 Tracking ID、GUI 当前绑定三个位置检查范围。若平台忽略筛选并返回其他 Key 的费用，明确报告 `COST_SCOPE_MISMATCH`，不回退全账户、不部分采用、不执行额外付费调用。
- 受管目标没有消费明细时报告 `NO_SELECTED_USAGE_DATA`，保留未知金额及已有记录，可继续周期读取；它本身不证明绑定错误。正额度不能据此删除，原零额度规则仍须身份和目标核验。
- 设为 `-1` 或未输入的目标不查询费用、不新增费用记录、不自动处理；已有历史账目、未决操作和账户连续性检查保留。完整 Key 列表仍用于身份与删除目标核验。
- README、使用说明和验证计划同步说明请求范围，并新增实际架构解释，明确当前没有 DSH 插件、网关、虚拟令牌或 `user_id` 注入。

## 改动理由

原正式费用 URL 只有 `start/end/tz`，确实会读取整个账户。此前保存的官方前端 `4179.a95866c86d.js` 在约 566478 字符处，费用函数接收 `apiKeyTrackingIds` 并传入 `api_key_tracking_id`。同套官方请求包装器 `8236.269153b691.js` 约 1178946 处将数组逐项追加为重复查询参数。这是已经观察到的控制台能力，过去代码漏用了它；不能据公开余额 API 只有账号余额，就推断控制台费用没有筛选。

脱敏源码摘录、位置、来源 URL 与 SHA-256 已保存到本地 `work/dev14-selection-20261103/official-scope-evidence.json`。这些观察支持实现，不代表内部接口稳定性承诺或本轮真实服务端验收。

dev13 新日志已确认模型和函数费用解析成功，但费用 ID 与当前受管目标无交集。旧全账户读取把“其他目标有消费、当前目标没记录”的情况送进账本零交集错误，因此用户看到费用与绑定不一致。这一错误本身不能证明账号切换，也不足以认定当前目标究竟零消费还是账单延迟。新版本把请求范围前移到服务端，并把指定范围空明细作为未知状态，不补零、不重新绑定。
