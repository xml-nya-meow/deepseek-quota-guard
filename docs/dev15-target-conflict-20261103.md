## 改动理由与问题分析

### 已确认的最新情况

- 运行日志确认版本为 `0.1.0rc6.dev14`，代码摘要与上轮候选包一致。
- 2026-11-03 13:21:49 至 13:22:33 共四次费用采集，HTTP 均为 200，平台业务码均为 0。
- 前三次所选范围无费用明细，返回 `NO_SELECTED_USAGE_DATA`；第四次成功解析一个受管 Tracking ID 的费用，且该 ID 与当前平台列表匹配。
- 四次结果到 GUI 后，全部在 `binding_verification` 阶段抛出普通 `GuardError`，最终显示“本地处理失败”；费用快照尚未写入。
- 最新这组日志没有执行删除，也没有 `KEY_TARGET_READ_FAILED`。此前删除预检问题必须单独调查，不能与此次费用入账失败混为一谈。

### 已缩小的代码范围

`App.collect()` 的回调在同一个 `binding_verification` 阶段连续执行：

1. `_claim_targets()` 取得 Windows 全机目标互斥；
2. `DataStore.bind_keys()` 核对平台名称与历史绑定；
3. 核对返回的受管 Tracking ID 范围。

第三步的异常类型为 `SnapshotApplyError`，账户不一致为 `AccountMismatch`，均与本轮记录的普通 `GuardError` 不同。当前优先排查前两步。

### 当前占用事实与证据限度

调查时仍存在旧 dev13 主进程及其工作、退出见证进程，dev14 已退出。公开记录不包含本机进程编号或账户身份。

- 使用 SQLite `mode=ro` 读取旧 dev13 当前账本，它有两枚活跃绑定；对其对应的 mutex 使用 `OpenMutexW` 查询，两个对象均存在。探测只打开并立即关闭自己的引用，不取得锁所有权，不释放旧进程的锁。
- dev14 原始账本和变更日期后的账本均为零绑定、零费用、零快照，符合“绑定之前被阻止”的现象；原始人员表有一个受管名称与旧活跃绑定名称重合。报告只记数量，不披露姓名或完整标识。
- 被检查的四个数据库在只读调查前后文件 SHA-256 均不变。
- 以随机合成 UUID 调用真实 Windows 互斥与 `App._claim_targets()`，能复现同样的普通 `GuardError` 路径：第一实例占用，第二实例失败；第一实例正常释放后，第二实例立即成功。

**已经确认：旧版本仍在运行，旧目标占用对象仍存在，且同类竞争会在当前代码绑定前阻断费用应用。它与本轮四次日志高度吻合，是当前最强、且可复现的解释。** 旧诊断没有记录是哪一个子步骤抛出异常，也没有保存当次完整列表；不能声称已逐条追溯证明四次都来自同一 mutex，更不能据此宣称所有历史失败都已解决。

“仍在运行的旧实例/退出见证”与“无主的磁盘临时文件”是不同问题。这套互斥由 Windows 对象及进程引用维持，删除磁盘锁文件、清浏览器缓存或改变日期不能解除其占用。正常关闭旧软件并等待独立浏览器清理完成，才是恢复步骤。本轮没有替用户关闭旧程序。

不能将当前证据解释成“只能读取今天”“日期写死”“平台未返回响应”或“只需重登录”：第四次带历史起点的费用请求和解析已经成功，失败发生在其后的本地处理阶段。

### 为什么上轮测试通过，使用中仍显示失败

原有 `test_target_conflict_stops_collection_before_binding_or_snapshot` 已验证冲突会阻止绑定和快照。保护本身按设计生效，测试没有断言错误代码、按钮文字、诊断阶段和关闭旧实例后的恢复路径。这是明确的诊断与验收遗漏，不能用“871 项通过”替代真实可用性结论。

现有代码仍对完整已观察 Key 列表取得互斥，即使某个 Key 不在本次费用查询名单。费用范围和防止多个管理器同时操作平台的保护范围是两件事。本轮不缩小互斥范围，以免把修复提示问题变成放开重复管理。
