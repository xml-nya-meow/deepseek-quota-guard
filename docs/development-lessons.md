# 开发教学：从费用读取到一次可核实的撤销

这份教程适合会读 Python、希望理解桌面自动化的读者。案例取自经典版最后一次修复（`0.1.0rc6.dev19`）。先沿代码回答三个问题：哪一行是我们负责的 Key？费用到了，可否提交删除？程序凭什么说目标已经消失？练习只用项目里的虚构数据和模拟传输，可以通过阅读完成。

## 一次失败为什么需要拆成三个问题

设人员表尾部有一行“样本丙”，额度是 0.20 元。在它前面插入十一行空姓名、额度为 `-1` 的空位。平台另有几枚普通 Key 和一枚 Harness 托管项。给样本丙两次虚构的累计费用 0.19 元、0.20001 元。项目已有一个测试覆盖这个场景。先猜第二次读取以后哪些记录应该改变，再看它的三个断言：费用请求只含受管身份，十一行都保持未分配，模拟提交只针对丙一次。[对应测试](../tests/test_sparse_managed_rows.py)

| 问题 | 能证明它的证据 | 不能靠哪一步代替 |
| --- | --- | --- |
| 费用是否到线 | 账本已接收适用期间的费用，规则指明是哪条额度触发 | 页面返回 HTTP 200 |
| 这次能否提交 | 已绑定的完整 Tracking ID、当前账户及完整列表一致，所选类型与参数通过，处理记录和一次性许可成立 | 姓名相同，或读到了超额金额 |
| 提交后发生什么 | 重新读取 HTTP 列表并刷新网页，核对目标缺席且其他已知身份仍在 | 删除请求得到成功响应，或 GUI 显示“待处理” |

下面分别追踪这三个证据。不需要连接控制台，也不需要输入任何真实 Key。

## 第一课：范围与身份是两张不同的表

人员表决定“要管谁”。空姓名的行始终未分配，已填写但额度为 `-1` 的行跳过管理。初次绑定时，程序要能由名称唯一确定平台上的 Key，之后持久保存完整 Tracking ID。中间有十几行空行，不能成为结束遍历的理由。公共人均额度出现在空行上，同样不会赋予管理资格。[绑定与判定代码](../quota_guard/core.py)

完整平台列表回答另一个问题，“这次看到的是原来那个账户的哪些对象？”因此身份核验要看到未参与管理的项目，包括应用托管项。费用请求则只带已填写并交给程序管理的 Tracking ID。没有受管目标时不发费用 GET。指定范围失败也不会改用全账户账单凑数。[受管费用请求](../quota_guard/platform_http.py) · [浏览器采集入口 `_collect`](../quota_guard/browser_service.py)

解析结果时，程序用 `Decimal` 汇总平台给出的金额，区分模型系列和函数系列。日期范围、分类结构或身份覆盖不满足条件时，程序要能说明这次读到了什么、哪些已有金额来自早先快照。把没有明细的目标补成零会改变后续决策，把每次刷新返回的累计额反复相加也会制造超支。[费用解析器](../quota_guard/cost_parser.py) · [快照应用 `apply_snapshot_result`](../quota_guard/core.py)

**动手读。** 在稀疏名单测试里找到第二次模拟读取。把丙的阈值在纸面上改成 0.21 元并假设公共额度更高。此时仍会读到 0.20001 元，但丙不再因个人额度触发。若姓名改为空白，则变化更早，丙连费用请求范围都不会进入。[稀疏名单练习](../tests/test_sparse_managed_rows.py)

## 第二课：排序不携带身份

在 2026-11-04 提供的两份只读列表样本里，目标在 HTTP 数组排第四，在网页可见表格排第一。两处的顺序都合法。这解释了为什么不能按表格行号、截图里的位置或“第一个可删除按钮”选目标。即使两份列表一样长，也可能属于不同的身份集合。[dev19 现场证据和合成复现](dev19-normal-key-contract-20261104.md)

读 `ConsoleKeyManager.read_target()` 时可以画两列。左列填写网页返回的完整 ID 与名称，右列填写 HTTP 返回的完整 ID、名称和类型。先核对所有身份，再用已绑定的完整 ID 在右列定位目标。对 `DSH` 用经过验证的 Harness 显示名称规则，对普通条目按实际名称比较。GUI 中用于定位的网页行也要重新读取完整 ID。换行只改变显示位置，替换身份则必须停止。[HTTP 目标适配](../quota_guard/platform_keys.py) · [网页行定位 `_key_row`](../quota_guard/browser_service.py)

| 所选条目 | dev19 的行为 |
| --- | --- |
| `NORMAL` 普通项 | 全部身份通过后，仅为该目标校验掩码标识和整数创建时间。掩码标识与另一项冲突时也会拒绝。 |
| `DSH` Harness 托管项 | 保留它作为账户身份的证据。即使人为给它补齐普通字段，普通撤销入口仍返回 `KEY_TARGET_NOT_DELETABLE`。 |
| 未分类类型，包括旧合成样本里的 `USER` | 旁观项的身份仍需独立成立。把它选作撤销目标时返回 `KEY_TARGET_KIND_UNSUPPORTED`。 |

历史上，dev17 把一个未经真实普通 Key 样本确认的 `USER` 枚举当作删除类型。dev18 把全表身份和单目标参数拆开，但仍未认出真正的普通类型。dev19 的依据是两份成功的只读列表响应，以及用户看到的托管行禁用控件。它们足以修订列表解析，并不能证明服务端接受实际删除。旧故障发生时的原始 HTTP 正文没有保留，所以只能说这组样本解释了可复现的失败路径。[合成夹具与来源说明](../tests/fixtures/platform_keys_contract_20261031.json)

**动手读。** 看排列测试如何使用四个虚构身份，把 HTTP 顺序和网页顺序分别枚举。共有 `4! × 4! = 576` 种组合，其中还包括同名普通项。每次检查模拟 POST 中的目标 ID、掩码与创建时间，并检查调用次数。再看第二个案例：一个旁观普通项缺少掩码，不妨碍定位丙；把缺字段的项本身选作目标则必须拒绝。[排列与字段测试](../tests/test_http_key_order.py)

## 第三课：给每种结果起准确的名字

“检查删除准备（只读）”和正式撤销共用 `_prepared_http_target()`。它检查完整列表、取得本次管理授权、读取所选目标参数，再复核账户。只读分支在这里返回并丢弃准备结果。真正执行时要重新检查，账本先记录操作并签发短时一次性许可，浏览器工作进程在发出唯一一次 POST 前消费许可。这样，一次通过的预检无法变成以后任意重发的凭据。[共有准备流程和核实逻辑](../quota_guard/browser_service.py) · [一次性许可](../quota_guard/revocation_permit.py)

| 诊断或记录 | 可以怎么解释 | 接下来读哪一层 |
| --- | --- | --- |
| 费用已应用，但“准备失败，未提交” | 这一轮费用可能已可靠入账，撤销请求尚未发送 | 查看失败阶段和固定原因码，分别核对身份、类型、授权或参数 |
| 已进入可能提交阶段，随后超时 | 请求是否生效未知 | 保留操作记录，走状态核实。自动重发可能再次作用于平台 |
| `absent_verified` | 新列表和网页均已核实目标缺席，另有已知身份支持账户连续性 | 这不能单独证明删除原因，也不能证明每个客户端的在途请求或后续调用会怎样 |

这个区分对用户尤其重要。如果按钮只显示“失败”，人们很容易把改日期、重登甚至重新提交都当成同一种修复。诊断应当告诉人最后完成了哪一步，是否已经越过提交边界，以及眼下能做的只读动作。对外反馈只需版本、时间、阶段、原因码和复现步骤。省去完整请求头、原始响应、账本及浏览器目录。[诊断收集与显示](../quota_guard/diagnostics.py)

## 给后继维护者的设计练习

设想平台明天多返回一个全新的类型。先在虚构样本中把它作为旁观项，再把它作为所选项。写下两种预期：只要全表身份可以独立证明，已知普通目标仍可继续预检；未知类型一旦成为目标，就要在提交前明确停止。接着让网页在准备过程中增删一个身份。即使所选 Key 的名字完全没变，账户证据已经变化，应重新建立完整观察。这样的测试比简单添加一个字符串别名更能说明为何变更安全。[分层准备测试](../tests/test_key_preparation_layers.py) · [撤销流程测试](../tests/test_layered_revocation_flow.py)

后续开发转到本地 AI 版。一个可用于两代程序的设计问题是：让助手解释“已达额、准备失败、未提交”，和让它决定哪个对象应该删除，有什么区别？前者可以依据确定的状态，把帮助内容讲清楚。后者会让一次不可恢复的操作依赖无法逐项证明的模型输出。账户、身份、阈值、许可与操作结果的判断都应有可重放的代码证据。新版的实际提供内容和验证范围以独立仓库为准。[本地 AI 版](https://github.com/xml-nya-meow/deepseek-quota-guard-ai)

## 经典版留档记录

- **实际改动**　最后一版把普通类型修正为只读样本中的 `NORMAL`，把 Harness 的 `DSH` 单独处理，网页行重排时按完整 ID 重新定位。旧仓保留教学源码、合成测试和此前的验证历程。
- **改动理由**　四项列表中，同一目标在两种来源里的位置不同，普通项和托管项所需字段也不同。仅凭顺序会选错目标，要求全部条目都具备普通删除参数会挡住有效目标。
- **已经运行的验证**　冻结前的 dev19 全量离线回归 948 项通过，0 跳过。120 项定向用例已含在其中，四项身份的 576 种顺序组合使用模拟传输。Windows 构建、窗口启退、内置浏览器空白页检查均已完成。此次留档沿用原有结果。[原验证记录](dev19-normal-key-contract-20261104.md)
- **仍未解决或未验证的事项**　dev19 在真实登录会话中的完整只读预检、单次撤销及独立核实未验收。正额度跨线后的完整周期、真实 Excel/WPS 导入、长期运行和并行桌面操作也未验收。网页完整列表读取上限是 200 行，超过上限停止，平台截图中普通 Key 容量为 300。旧版测试至此结束。此前版本的强制删除和零额度首轮成功，只适用于当时记录的场景。[历史记录](测试历程-截至2026-11-02.md)
