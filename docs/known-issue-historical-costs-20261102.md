## 改动理由

此前的通用“读取失败”不能区分平台请求失败、费用解析失败和本地账本拒绝。仅凭按钮状态，容易将不同原因统一归为日期写死、缓存或残余进程。

当前费用流程使用登录后的独立浏览器会话取得控制台授权，再按账本起点和 UTC+8 截止日期构造 HTTP GET 参数；不通过点击日历选择日期。浏览器会话保留授权材料，费用响应不作为跨次读取的缓存复用。取得费用后，仍需通过 Tracking ID、账本期间和累计金额等本地核验。

费用 Tracking ID 与账本绑定没有交集时，原保护逻辑拒绝应用，以免把其他 Key 的费用记到当前受管 Key。不能为了显示成功而按相同名称合并不同 Key，也不能把缺失费用补成零。

数量不能证明具体 Key 身份。“费用属于已经删除的旧 Key”“当前新 Key 尚无消费”“绑定或接口映射有误”仍是待核对方向，不能据此确认其中任一个。

随后进行了本地账本只读比较：三个已绑定账本的起点分别为 09-29、11-02、10-29，账户标记与绑定集合相同；两个绑定均为 active，退休绑定数为 0。读取前后数据库摘要一致。**这次没有出现“改日期就改变账户或绑定”的情况**；“全部绑定 2、受管 1”不能解释为“另一个一定已经退休”。费用响应未保存原始标识，因此目前仍不能确认无交集的具体成因。

源码进一步核对：费用身份读取自 `api_key.tracking_id`，模型字段单独用于费用分类；页面按 Tracking ID 表头定位并校验完整 UUID。空明细分支也先完成身份核验，不是绕过身份检查后直接成功。日期进入费用快照摘要是期间隔离，不等于改变账户身份。有关固定 30 天跨度的社区说法尚无足够证据对应本次业务拒绝，不据此修改正式查询范围。

同时检查了源码中日期参数、费用响应读取和绑定交集核验。没有为本轮诊断登录真实账户、发起付费模型调用或提交 Key 撤销；原始日志、凭据和账本未随本次文档上传。
