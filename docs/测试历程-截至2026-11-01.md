## 一、实际改动

- **dev0 至 dev2：从图标点击迁移到控制台 HTTP。** dev0 已能读取费用并判断额度，但真实删除被图标结构匹配阻断。dev2 根据平台公开前端契约实现同一独立浏览器会话内的管理请求，保留完整目标核验、先落账、一次性许可、单次提交和独立结果核实。没有把原生 Key 管理改成代理网关。
- **dev3：补齐准备与结果核实。** 在首次必要列表导航前监听请求；事件回调排队，轮询阶段读取限定头；细分准备失败原因。增加独立单次删除，与全自动管理共用执行器。提交后核对新鲜 HTTP 列表及重载页面列表，不能只凭 HTTP 200 判成功。
- **dev4：拆分预检、调度和费用证据。** 增加只读删除准备检查；管理间隔默认 10 秒，可设 1～3600 秒，与固定 300 秒费用有效期分离。修复 Windows 短路径别名造成的临时目录回收误拒绝，以及浏览器自检异常无法正常退出。
- **dev5：窄修请求头兼容。** 仅允许已有公开前端依据的空 `x-device-model`，与字段缺失分开处理；其余空头及非法内容仍拒绝。诊断只记受控字段名、类型、长度、来源和原因，不记凭证。失败清理授权与候选材料，保留提交去重保护。
- **函数费用仍处于候选阶段。** 抽取共用费用解析器，新增普通与 `function_series` 混合费用的离线入口；正式采集仍拒绝非空或异常函数系列，没有界面或环境变量开启开关。

## 二、改动理由

视觉图标不是稳定的管理契约，继续累加 SVG 签名难以维护。控制台 HTTP 也属于可能变化的内部接口，因此仍需身份、目标、会话和结果检查；没有稳定官方管理 API 或服务端幂等承诺的结论。

dev2 两次真实失败均停在约 15 秒的准备阶段。旧日志不足以区分请求未出现、授权校验或弹窗问题，不能将邮箱提醒或网页二次确认写成已证实根因。网页二次确认是人工提交入口的一部分，不能解释所有软件准备失败。

dev4 日志进一步将两次失败定位为本地 `authorization / KEY_CLIENT_HEADER_INVALID`，均记为 `not_submitted`，并非服务端已经拒绝删除。公开前端明确构造空设备型号，支持 dev5 的窄修；dev5 真实运行随后观察到该空头被接受，但旧日志没有具体头名，仍不能追溯断言旧故障只有这一个原因。

原业务规则继续保留：`-1` 跳过、零额度按原规则处理、正额度用 Decimal 比较、任一额度达到即触发、公共额度按原规则计算、未知费用不记零。轮询变快不会消除平台出账延迟或在途费用；“待处理”是本地状态，不能冻结原生 Key。
