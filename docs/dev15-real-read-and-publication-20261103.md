## 改动理由

此前“读取失败”混合了多个阶段。HTTP 成功只证明 HTTP 通信完成；解析、目标占用、绑定、账本应用和导出仍须分别核验。dev14 的较早四次采集中，请求均成功，但旧日志将取得互斥和绑定校验归在同一阶段；旧管理器仍有目标占用是可复现的强解释，却不能事后逐条证明四次异常来自同一个 mutex。dev15 增加准确的阶段与原因码，保留原保护，不通过杀进程、清账本或改日期绕过。

本轮成功读取已包含历史起点，因此“只有开发当天能读取”的旧观察不能继续作为当前结论。日期仍是动态请求范围和快照期间的一部分，不是账户身份。更早的长区间业务拒绝、费用归属不匹配以及旧删除预检失败仍有各自的未决问题，不能因这两次成功而一并关闭。

### 两份外部分析的帮助与适用范围

- 网页 GPT 的第八轮审查属于文档和已提供证据的复核，没有实际运行本地源码。它提醒区分 Windows mutex 的所有权与仍存活的对象引用、核对句柄关闭与部分失败回滚，以及用真实恢复链路验收。这些方向有帮助，需逐项对照现有实现和测试，不能把建议当成已经发现的现网根因。
- DSH 的根因分析明确记载 GitHub 获取受阻，实际依据是本地交接目录的 dev14 源码快照、日志及 dev15 调查说明。它帮助定位 `_claim_targets()` 在绑定之前，支持把保护冲突与绑定错误分开；它不是对 GitHub dev15 当前源码的独立完整审计。
- 已核对的现有覆盖包括：冲突时关闭新获得的句柄但不释放其他所有者、批量取得部分失败后的正常回滚、真实子进程竞争的整批回滚、同一对象去重与重复关闭、剩余引用阻止新所有者，以及旧合成锁释放后在同一窗口连续重新读取恢复。已有测试不机械重复添加；原生跨进程测试也不等于已经验证不同 Windows 登录会话的全部组合。
- “冲突后保持已核验状态”不能直接照搬。软件可以保留浏览器会话并允许直接重新读取，同时使旧的账户、目标和费用核验资格失效；重新读取仍须取得新证据。没有采用绕过锁、自动结束旧实例、缩小锁保护范围或改造成网关的建议。
- 额外复核确实发现一个极端清理恢复缺口：目标锁构造过程中部分取得失败，又叠加回滚释放失败时，构造函数没有返回对象，界面可能拿不到对象以重试清理。纯内存故障注入可复现；现有回滚失败测试主要覆盖已经构造成功对象的 `update()`，不能覆盖该组合。尚无本轮真实发生证据，已列入后续，不把它认定为此前四次失败的确定原因。本次未修改运行代码处理这一组合。
